> **실제 압축 해제 길이와 할당한 버퍼 크기를 혼동하면 어떤 일이 생길까?** MongoBleed를 로컬 환경에서 재현하며, 조작된 메시지가 메모리 정보 노출로 이어지는 과정과 패치 전후의 차이를 살펴봤다.

MongoDB에서 공개된 **MongoBleed(CVE-2025-14847)** 취약점을 대상으로 공개 PoC의 동작을 분석하고, Docker 기반 테스트 환경에서 직접 재현해 보았다.

이번 실습의 목표는 **취약한 입력이 MongoDB 내부에서 어떤 처리를 거쳐 메모리 정보 노출로 이어지는지 이해하는 것**이었다. PoC 실행 결과를 저장하고 Wireshark로 요청과 응답을 확인한 뒤, 패치된 버전에서도 같은 방식으로 테스트했다.

| :--- | :--- |
| **분석 대상** | MongoBleed · `CVE-2025-14847` |
| **핵심 분석 지점** | `OP_COMPRESSED`, zlib 압축 해제 길이, BSON 오류 응답 |
| **재현 환경** | 로컬 Docker 기반 MongoDB 컨테이너 |
| **비교 버전** | MongoDB `6.0.26` → `6.0.27` |

## 01. MongoBleed란?

MongoBleed는 MongoDB의 **zlib 압축 메시지 처리 과정에서 초기화되지 않은 힙 메모리가 노출될 수 있는 취약점**이다. MongoDB에 네트워크로 접근할 수 있는 클라이언트가 인증하지 않은 상태에서도 이를 유발할 수 있다.

핵심은 압축 메시지에 선언된 길이와 실제 압축 해제 길이의 불일치다. 서버가 실제 데이터보다 넓은 메모리 영역을 유효한 메시지로 취급하면, 후속 처리 과정에서 기존 힙 메모리의 일부를 읽을 수 있다.

| 항목 | 내용 |
| :--- | :--- |
| **CVE** | `CVE-2025-14847` |
| **취약점 유형** | 초기화되지 않은 힙 메모리 읽기에 따른 정보 노출 |
| **인증 필요 여부** | 인증 이전 단계에서 발생 가능 |
| **심각도** | MongoDB CNA 기준 CVSS v4.0 **8.7 · High** |
| **이번 실습 대상** | MongoDB `6.0.26`의 zlib 압축 메시지 처리 |

인증 조건과 심각도는 [NVD에 등록된 MongoDB의 CVE 정보](https://nvd.nist.gov/vuln/detail/CVE-2025-14847)를 기준으로 정리했다.

## 02. 취약점이 발생하는 원리

### OP_COMPRESSED 메시지 구조

MongoDB는 네트워크 통신량을 줄이기 위해 기존 메시지를 압축하고, 이를 `OP_COMPRESSED` 메시지로 감싸서 전송할 수 있다.

| 필드 | 역할 |
| :--- | :--- |
| `MsgHeader` | 메시지 길이, 요청 식별자, opcode 등 공통 헤더 |
| `originalOpcode` | 압축하기 전 원본 메시지의 opcode |
| `uncompressedSize` | 공통 헤더를 제외한 **압축 해제 결과의 크기** |
| `compressorId` | 사용한 압축 알고리즘의 식별자 |
| `compressedMessage` | 공통 헤더를 제외한 원본 메시지 본문의 압축 데이터 |

공식 명세에서 `OP_COMPRESSED`의 opcode는 `2012`, `OP_MSG`는 `2013`이며, zlib의 `compressorId`는 `2`다. [MongoDB Wire Protocol 공식 문서](https://www.mongodb.com/docs/manual/reference/mongodb-wire-protocol/)

### 실제 데이터 길이와 버퍼 크기의 불일치

공격자는 **실제 압축 해제 결과보다 큰 `uncompressedSize`**를 선언할 수 있다. 서버는 선언된 크기에 맞춰 버퍼를 준비하지만, 실제 압축을 해제하면 그 앞부분만 데이터로 채워질 수 있다.

문제는 압축 해제 결과를 반환할 때 발생한다. 취약한 처리에서는 실제로 채워진 길이 대신 할당된 버퍼 크기를 반환해, 나머지 영역까지 후속 메시지 처리에 포함될 수 있다.

```text
압축 해제용 버퍼
┌──────────────────────┬────────────────────────────┐
│ 실제 압축 해제 데이터 │ 초기화되지 않은 나머지 영역 │
└──────────────────────┴────────────────────────────┘
└─ 실제 데이터 길이 ───┘
└────────────── 할당된 버퍼 크기 ────────────────────┘
```

### BSON 파싱 오류가 응답으로 이어지는 과정

공개 PoC는 BSON 문서의 길이도 조작한다. 후속 BSON 파싱 과정에서 남은 메모리가 필드명으로 읽히고, 파싱 오류를 설명하는 응답에 그 내용이 포함될 수 있다.

```text
조작된 OP_COMPRESSED 요청
        ↓
실제 압축 해제 결과보다 큰 버퍼 준비
        ↓
버퍼 앞부분에만 압축 해제 데이터 기록
        ↓
실제 데이터 길이 대신 버퍼 전체를 유효한 영역으로 취급
        ↓
BSON 파서가 초기화되지 않은 영역을 필드명 등으로 읽음
        ↓
오류 응답에 기존 힙 메모리 조각이 포함될 가능성
```

이 흐름은 [공개 PoC의 설명과 코드](https://github.com/joe-desimone/mongobleed)를 바탕으로 정리했다. 핵심은 **서버가 메모리 조각을 오류 응답의 일부로 되돌려줄 수 있다는 점**이다.

## 03. 실습 환경

재현은 **로컬 Docker 기반 테스트 환경**에서 진행했다. Python PoC가 별도로 구성한 MongoDB 컨테이너에 요청을 보내고 응답을 수집하는 구조다.

| 구성 | 버전·용도 |
| :--- | :--- |
| **Docker Desktop** | `4.66.0` |
| **MongoDB · 재현 대상** | `6.0.26` |
| **MongoDB · 패치 비교** | `6.0.27` |
| **Python** | `3.13.1` |
| **Wireshark** | 요청·응답 패킷 확인 |

```text
Python PoC ── TCP 요청 ──▶ 로컬 MongoDB 컨테이너
           ◀─ 오류 응답 ──
                  │
                  └─ Wireshark로 통신 확인
```

이 글의 재현 결과는 직접 구성한 테스트 환경에서 관측한 내용이다.

## 04. 공개 PoC 코드 분석

실습에 참고한 코드는 Joe Desimone이 공개한 [`mongobleed.py`](https://github.com/joe-desimone/mongobleed/blob/main/mongobleed.py)다. 요청 생성부터 결과 저장까지의 흐름을 네 단계로 나누어 살펴봤다.

### 1. 조작된 요청 생성

PoC는 길이를 조작한 BSON 데이터를 만들고, `OP_MSG` 본문으로 구성한 뒤 zlib으로 압축한다. 이후 압축 결과를 `OP_COMPRESSED` 구조로 감싼다.

| 값 | 의미 |
| :--- | :--- |
| `originalOpcode = 2013` | 압축 전 메시지가 `OP_MSG`임을 표시 |
| `uncompressedSize` | 실제 압축 해제 결과와 별도로 지정하는 길이 |
| `compressorId = 2` | zlib 압축 사용 |
| `compressedMessage` | 조작된 BSON을 포함한 압축 데이터 |

여기서 **BSON에 선언한 문서 길이와 압축 해제 결과로 선언한 길이는 서로 다른 값**이다. 두 길이가 각각 BSON 파싱과 압축 해제 후 메시지 처리에 어떻게 사용되는지 연결해서 보는 것이 중요했다.

### 2. TCP로 전송하고 응답 복원

생성한 메시지는 TCP 소켓을 통해 로컬 MongoDB 서버에 직접 전달한다. 일반 MongoDB 드라이버를 사용하는 대신 **Wire Protocol 메시지를 직접 생성하고 전송하는 방식**이다.

응답은 한 번의 수신으로 모두 도착한다고 가정하지 않는다. 응답 헤더의 메시지 길이를 확인하고, 해당 길이에 도달할 때까지 데이터를 받아 하나의 메시지로 복원한다.

### 3. 오류 응답에서 데이터 추출

수신한 응답이 `OP_COMPRESSED`라면 압축을 해제하고, 그렇지 않으면 공통 헤더 이후의 본문을 읽는다.

공개 PoC는 본문에서 **BSON 오류에 포함된 필드명과 인식하지 못한 타입 값**을 찾아 데이터를 추출한다. 따라서 결과를 해석할 때는 메모리 조각이 오류 메시지의 어떤 부분에 포함됐는지 살펴봐야 한다.

### 4. 중복을 제거하고 파일로 저장

PoC는 문서 길이를 바꿔 가며 요청을 반복하고, 응답에서 추출한 조각을 모은다. 이미 수집한 조각은 중복을 제거한 뒤 바이너리 파일로 저장한다.

```text
요청 생성 → 전송 → 응답 복원 → 데이터 추출 → 중복 제거 → 파일 저장
```

저장한 파일을 문자열로 살펴보면서 어떤 정보가 포함되어 있는지 확인했다.

## 05. 실제 재현 결과

실습 결과에서는 **테스트용으로 DB에 넣어둔 문자열 일부와 Docker·컨테이너 환경에 관련된 경로**를 확인할 수 있었다.

| 구분 | 실습에서 확인한 내용 | 해석 |
| :--- | :--- | :--- |
| **테스트 DB 데이터** | 토큰·Secret Key 형태로 넣어둔 문자열 일부 | 처리했던 정보의 조각이 메모리에 남아 있다면 노출될 가능성 |
| **Docker 런타임 정보** | containerd·overlayfs 관련 경로 | 실행 환경에 관련된 문자열 노출 |
| **컨테이너 내부 정보** | 데이터 볼륨, `/data/db`, 시스템 경로 | 컨테이너의 저장·마운트 구조를 추정할 단서 |

### 테스트 DB에 넣어둔 문자열

테스트용 토큰과 Secret Key 형태의 문자열 일부가 수집 결과에서 확인됐다. 이를 통해 DB가 처리했던 정보가 프로세스 메모리에 남아 있을 경우, 취약점을 통해 조각 형태로 노출될 가능성을 확인했다.

### Docker·컨테이너 관련 경로

Docker Desktop과 containerd의 overlayfs 관련 경로는 다음과 같은 형태였다.

```text
/var/lib/desktop-containerd/...
```

데이터 볼륨과 컨테이너 내부 파일시스템에 관련된 문자열도 확인됐다.

```text
/docker/volumes/mongobleed-poc_mongodb_data/_data
/data/db
/etc/resolv.conf
/etc/hostname
/etc/hosts
/proc
/dev
/sys
```

> **결과의 의미:** 노출된 문자열은 DB 데이터뿐 아니라 실행 환경의 단서도 제공했다. 경로 문자열이 발견됐다는 사실이 해당 파일의 내용 전체를 읽었다는 의미는 아니다.

## 06. Wireshark로 확인한 요청과 응답

PoC 실행 결과와 함께 Wireshark에서 실제 통신을 살펴봤다. 코드가 만든 메시지가 TCP로 전달되고, 서버의 오류 응답으로 돌아오는 과정을 연결해서 확인했다.

| 확인 지점 | 살펴본 내용 |
| :--- | :--- |
| **요청** | Python PoC가 생성한 MongoDB 메시지의 전송 |
| **응답** | MongoDB가 반환한 BSON 파싱 오류 |
| **노출 문자열** | 응답의 오류 메시지와 함께 확인되는 overlayfs·containerd 관련 문자열 |

```text
PoC 메시지 생성
    → TCP 전송
    → MongoDB 압축 해제·BSON 파싱
    → 메모리 조각이 포함된 오류 응답
    → PoC에서 해당 조각 추출
```

코드의 출력만 볼 때보다 패킷을 함께 확인했을 때 **요청 생성 코드, 서버의 처리 결과, 추출된 문자열 사이의 관계**를 더 명확하게 이해할 수 있었다.

## 07. 패치 전후 비교

취약한 환경의 결과를 확인한 뒤 MongoDB를 **`6.0.27`로 업데이트**하고 같은 방식으로 다시 테스트했다. 이 버전은 MongoDB가 [SERVER-115508](https://jira.mongodb.org/browse/SERVER-115508)에 안내한 수정 버전 중 하나다.

### 패치가 바꾼 길이 처리

zlib 압축 해제 함수의 핵심 수정은 **할당된 버퍼 크기가 아니라 실제 압축 해제된 길이를 반환하는 것**이다. 아래는 반환값의 차이만 발췌한 비교다.

```diff
- return output.length();
+ return length;
```

`length`는 zlib의 `uncompress()` 호출 이후 실제 출력 길이로 갱신된다. 수정된 반환값은 [MongoDB 수정 커밋의 소스](https://github.com/mongodb/mongo/blob/505b660a14698bd2b5233bd94da3917b585c5728/src/mongo/transport/message_compressor_zlib.cpp#L58-L70)에서 확인할 수 있다.

### 같은 방식으로 다시 테스트한 결과

| 비교 항목 | 패치 전 · `6.0.26` | 패치 후 · `6.0.27` |
| :--- | :--- | :--- |
| **테스트 방식** | 공개 PoC 요청 전송 | 같은 방식으로 재테스트 |
| **메모리 정보 노출** | 테스트 문자열·환경 관련 경로 확인 | 기존과 같은 노출 결과는 확인되지 않음 |

이번 비교를 통해 버전 번호뿐 아니라 **길이 처리의 수정이 실제 응답 결과에 어떤 차이를 만드는지** 살펴볼 수 있었다. 패치 후 결과는 이번 실습 조건에서 동일한 노출을 관측하지 못했다는 범위로 해석했다.

## 08. 대응 방법

가장 우선적인 대응은 **취약점이 수정된 버전으로 업데이트하는 것**이다. 이번 실습의 `6.0.27`은 6.0 계열에서 비교한 수정 버전이며, 운영 환경에서는 사용 중인 계열의 보안 공지와 지원 상태를 함께 확인해야 한다.

| 우선순위 | 대응 | 목적 |
| :--- | :--- | :--- |
| **1** | 수정된 버전으로 업데이트 | 취약한 길이 처리 로직 수정 |
| **2** | 즉시 업데이트하기 어렵다면 서버의 허용 압축 알고리즘에서 `zlib` 제외 | 취약한 압축 처리 경로의 사용 차단 |
| **3** | 인터넷 직접 노출 제한 및 방화벽·접근 제어 적용 | MongoDB에 접근할 수 있는 네트워크 범위 축소 |

MongoDB는 즉시 업데이트할 수 없는 경우 `mongod` 또는 `mongos`의 `networkMessageCompressors`나 `net.compression.compressors` 설정에서 `zlib`을 제외하도록 안내한다. [MongoDB 공식 대응 안내](https://jira.mongodb.org/browse/SERVER-115508)

인증 이전 단계에서 발생할 수 있는 취약점인 만큼, **계정 인증과 함께 네트워크 접근 범위도 관리해야 한다.**

## 09. 실습을 마치며

이번에는 취약점 설명을 읽는 데서 출발해 프로토콜과 공개 PoC를 분석하고, 재현 결과와 패치 전후 동작까지 이어서 확인했다.

1. **CVE 조사:** 취약점의 영향과 인증 조건 확인
2. **프로토콜 분석:** `OP_COMPRESSED`와 길이 필드의 의미 파악
3. **PoC 분석:** 요청 생성·응답 수신·데이터 추출 과정 확인
4. **로컬 재현:** Docker 기반 테스트 환경에서 실행
5. **패킷 확인:** Wireshark로 코드와 실제 통신 연결
6. **결과 분석:** 테스트 문자열과 환경 관련 경로 확인
7. **패치 재검증:** `6.0.26`과 `6.0.27`의 결과 비교

가장 기억에 남은 부분은 **MongoDB의 메시지 구조와 길이 처리 방식을 이해하는 과정**이었다. 처음에는 `uncompressedSize`를 조작하는 것이 어떻게 정보 노출로 이어지는지 감이 잘 오지 않았다. 압축 해제 함수의 반환값, 후속 BSON 파싱, 오류 응답을 함께 보면서 그 연결을 이해할 수 있었다.

DB에 넣어둔 문자열 외에도 Docker와 컨테이너 내부 경로가 나타난 점도 인상적이었다. 메모리 정보 노출은 데이터의 조각뿐 아니라 실행 환경을 추정할 수 있는 정보까지 드러낼 수 있었다.

앞으로 다른 CVE를 분석할 때도 **취약한 입력이 프로그램 내부에서 어떤 처리를 거쳐 보안 문제로 이어지는지 추적하고, 가능하면 패치 전후를 직접 비교하는 방식**으로 공부해 보고 싶다.
