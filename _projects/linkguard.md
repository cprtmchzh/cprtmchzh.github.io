> **웹페이지에서 수집한 증거를 바탕으로 악성 URL을 판단, 판정 이유와 관련 근거를 제공하는 AI 보안 서비스**

| 항목 | 내용 |
| :--- | :--- |
| **진행 과정** | 2026 AI보안 기술개발 교육과정 (제한구역 팀, 6인) |
| **산출물** | 웹 서비스, Chrome Extension, URL 수집 및 관측 자료 저장 파이프라인 |
| **주요 성과** | MobiSec 2026 포스터 논문 채택 (*Two-Stage Evidence-Based AI Analysis for Unknown Malicious URLs*) |
| **담당 역할** | L3(HTML·JavaScript) 정적 분석 개발, L4 심층 분석용 Agent Tool 개발, 프론트엔드·백엔드 연동 |

LinkGuard는 URL 구조, 도메인·인프라, HTTP·TLS, HTML·JavaScript 정보를 분석하는 **빠른 분석(L0~L3)**과, 사용자의 질문에 따라 Agent가 격리된 브라우저에서 페이지의 실제 동작을 조사하는 **심층 분석(L4)**의 2단계로 구성된다. 사용자는 웹 서비스와 Chrome Extension을 통해 URL을 검사하고, 판단에 사용된 근거와 추가 조사 결과를 단계적으로 확인할 수 있다.

---

## 01. 문제 정의와 설계 목표

최근 AI로 인하여 악성 URL 생성 및 할동 종료 시점이 매우 짧아졌다. 때문에 기존의 외부 위협 인텔리전스나 블랙리스트 기반 평판 조회 만으로는 악성 URL 탐지하기 어려워지고 있다.

따라서 LinkGuard는 **분석 시점에 외부 평판으로 확인되지 않은 URL을 자체 수집 증거만으로 분석하고, 그 결과를 납득할 수 있게 설명하는 것**을 목표로 삼았다.

1. **자체 증거 기반 분석:** 외부 평판에 의존하지 않고 페이지 내 정보를 통해 직접 단서를 확보.
2. **구체적인 판정 이유 제시:** 수집한 개별 증거들의 의미와 상호 관계를 해석하고 내린 판정에 대한 설명.
3. **판정 이유와 원본 근거의 연결:** 설명에 사용된 실제 관측 데이터를 사용자 화면에서 요약부터 상세 기술정보까지 펼쳐 볼 수 있게 연결.

## 02. 서비스 구성과 사용 흐름

| 기능 구분 | 상세 설명 |
| :--- | :--- |
| **빠른 URL 분석** | URL 구조, 도메인·인프라, HTTP·TLS, 페이지 콘텐츠를 병렬 분석해 판정 결과와 이유를 제공한다. |
| **상세 근거 확인** | 판정 이유에 연결된 실제 관측 사실과 기술정보를 단계적으로 펼쳐 볼 수 있다. |
| **Agent 기반 심층 분석** | 사용자가 입력한 질문을 바탕으로 격리 환경에서 페이지의 유도 과정과 실제 동작을 조사한다. |
| **조사 진행 표시** | 심층 분석 중 수행 중인 업무·작업 상태와 격리 브라우저의 실시간 화면 캡처를 제공한다. |
| **Chrome Extension** | 브라우저에서 즉시 URL 검사를 요청하고, 웹 서비스의 상세 결과 화면으로 이동할 수 있다. |

1. **URL 제출 및 빠른 분석:** 사용자가 웹이나 확장 프로그램에서 URL을 제출하면 빠른 분석이 실행된다.
2. **근거 확인 및 외부 평판 대조:** 분석이 완료되면 판정 결과와 이유, 연결된 근거를 확인한다. VirusTotal 조회는 선택적 참고 기능으로 제공하며, 자체 분석 결과와 외부 조회 결과를 분리해 보여준다.
3. **심층 분석 요청 (선택):** 정적 분석만으로 확인하기 어려운 동적 유도 과정이나 특정 의심 정황이 있을 경우, 사용자가 질문을 입력해 Agent 기반 심층 분석을 요청한다.

## 03. 시스템 아키텍처

기본 처리 흐름은 **증거 수집(L0~L3) → 판단 맥락 구성(Context Builder) → LLM 판정(Judgment) → 결과 제공**으로 이어진다. 심층 분석(L4)은 빠른 분석 결과를 확인한 뒤 사용자가 요청할 때 실행되는 별도 파이프라인이다.

![URLGuard 시스템 아키텍처]({{ '/assets/uploads/urlguard_architecture.png' | relative_url }})

| 계층 | 분석 대상 | 주요 관측 내용 |
| :--- | :--- | :--- |
| **L0** | URL 문자열과 구조 | 호스트·경로·파라미터 구성 등 주소 자체의 구조적 특징 |
| **L1** | 도메인·인프라 | DNS 레코드, IP·ASN, RDAP 도메인 등록 정보 |
| **L2** | HTTP·TLS | 응답 헤더·상태, 리다이렉트 체인, 파일 형식, TLS 인증서 정보 |
| **L3** | HTML·JavaScript | 입력 폼과 제출 대상의 관계, 스크립트 내 데이터 흐름과 동작 선언 |

## 04. 핵심 모듈 상세 설계

### 1) L0: URL 구조 분석

웹페이지에 접속하기 전, WHATWG 파서로 URL을 해석하고 **6개 그룹의 18개 검사**를 수행한다. 주소에 포함된 호스트, 경로, 파라미터와 문자열의 구조를 분석해 후속 판단에 필요한 단서를 확보한다.

| 검사 그룹 | 주요 항목 |
| :--- | :--- |
| **호스트 구조** | IP 호스트, 의심 TLD, 무료 발급 도메인, 비표준 포트 |
| **텍스트 트릭** | 콤보스쿼팅, 타이포스쿼팅, 퓨니코드 위장 |
| **링크·파일** | 파일 다운로드, 이중 확장자, 단축 URL |
| **파라미터** | XSS, 오픈 리다이렉트 |
| **문자열 구조** | DGA 패턴, 긴 URL, Base64 인코딩, 접속 호스트 교란, 서브도메인 구조 이상 |
| **기타** | 비표준 프로토콜 |

---

### 2) L1: 도메인·인프라 분석

접속 호스트와 등록 도메인을 구분하고, **DNS·IP·ASN·RDAP 정보**를 수집한다. 주소가 실제로 어디에 연결되는지와 도메인 등록 정보를 확인해 URL 문자열만으로 알기 어려운 인프라 맥락을 제공한다.

* **주소 단위 구분:** 접속 호스트, 등록 도메인, 사이트별 책임 경계를 구분.
* **DNS 조회:** 접속 호스트의 A·NS와 CNAME 연결을 확인하고, 등록 도메인이 다르면 해당 도메인의 NS 조회.
* **IP·ASN 조회:** 접속 IP의 네트워크 번호, 대역, 조직, 국가 정보 수집.
* **RDAP 조회와 대조:** 등록일·만료일·최근 변경일·도메인 상태·등록대행사를 확인, 같은 등록 도메인의 DNS와 RDAP 네임서버 정보 대조.

---

### 3) L2: HTTP·TLS 분석

**HTTP 9개, 인증서·TLS 7개, CT 기록 1개 등 총 17개 항목**으로 응답과 이동 경로, 다운로드 관련 정보, 연결의 인증서·TLS 상태를 분석한다.

* **HTTP 이동 경로:** 리다이렉트 경로와 등록 도메인 변경, IP 주소로의 이동, 단축 URL, Refresh 헤더, HTTPS에서 HTTP로의 이동 확인.
* **응답·다운로드:** Content-Type과 파일 형식의 관계, 실행 파일 형식, 첨부파일 다운로드 지시 분석.
* **인증서·TLS:** 유효기간과 시작 시각 이후 경과일, 접속 호스트와 인증서 이름의 일치, 자체 서명 여부, 인증서 체인 검증, 협상된 TLS 버전, 와일드카드 이름 확인.
* **CT 기록:** 인증서의 내장 SCT 시각을 우선 사용하고, 없으면 인증서 지문으로 crt.sh를 조회해 확보한 기록의 시각과 출처를 기록.

---

### 4) L3: HTML·JavaScript 정적 분석

수집된 HTML과 JavaScript 소스를 입력받아 페이지 내부의 구조와 데이터 흐름 관계를 정적으로 분석한다. **HTML 8개, JavaScript 9개 등 총 17개 분석 항목**을 다루며, 항목별 관측 사실과 함께 정적으로 해석하지 못한 미확정 영역도 명시적으로 기록한다.

* **HTML 구조 분석:**
  * **인증정보 제출 구조:** 비밀번호 등 인증정보 입력 필드를 소속 `form`에 연결하고 전송 방식(method)과 목적지(action)를 확인.
  * **페이지 이동 선언:** `meta refresh`는 자동 이동 선언으로 해석하고, `base href`는 상대 URL의 기준 주소로 처리해 각 요소가 가리키는 대상과 현재 문서의 관계 기록.
* **JavaScript AST 분석:**
  * **Esprima 기반 구문 분석:** 코드를 함수 호출, 변수, 조건문 등의 문법 구조(AST)로 변환해 동적 실행 API 호출, 디코딩과 실행의 결합, 외부 스크립트 삽입, 네트워크 요청 목적지 등을 추출.
  * **데이터 흐름 추적:** 단순히 입력 필드 접근 코드와 외부 요청 코드가 한 파일에 함께 존재한다는 이유만으로 유출 관계로 단정하지 않으며, 코드상에서 값이 실제로 이어지는지 확인.

> **관측 범위의 구분:** L3가 제공하는 결과는 수집된 소스 코드에서 **정적으로 확인한 선언과 구조**이며, 실제 클릭, 값 입력, 외부 전송의 성공 여부는 L4의 동적 관찰 영역과 엄격히 구분.

---

### 5) Context Builder: 판단 맥락 재구성

L0~L3에서 수집한 원본 기록을 그대로 LLM에 전달하면 중복 정보가 많아지고 연관된 사실들이 흩어져 판단 효율이 떨어진다. Context Builder는 수집된 기록을 관측 대상과 관계 중심으로 묶어 모델이 종합 판단에 집중할 수 있는 형태로 재구성한다.

| 처리 단계 | 주요 작업 및 목적 |
| :--- | :--- |
| **중복 제거와 선별** | 계층 간 반복되는 공통 정보를 정리, 시스템 실행 관리용 메타데이터는 모델 입력에서 제외. |
| **증거 구조화** | 동일한 인증서나 특정 입력 폼처럼 하나의 대상에 속하는 여러 관측 사실과 관계를 하나로 통합. |
| **의미와 판단 안내 구성** | 개별 검사 결과의 보안상 의미, 정적 관측의 해석 범위, 다른 증거와 교차 검토할 가능성을 함께 안내. |
| **다중 출력 생성** | LLM 입력용 문서, 사용자 화면 표시용 상세 근거, 내부 추적용 원본 매핑 데이터를 각각 생성. |

예를 들어 URL에 유명 서비스 이름이 포함된 경우, 해당 이름이 실제 등록 도메인(eTLD+1)인지 서브도메인이나 경로에 포함된 문자열인지 구분해 명시한다. 주소의 표면적 표현과 실제 접속 대상의 관계를 구조화해 제공함으로써, 모델이 페이지 내 폼 구조 등 다른 증거와 결합해 피싱 여부를 정확히 판단할 수 있도록 돕는다.

---

### 6) Judgment: LLM 판정과 근거 매핑

Context Builder가 구성한 문서를 바탕으로 LLM이 최종 판정, 요약, 판정 이유를 작성한다. 판정 결과는 다음 5단계로 구분된다.

`정상` · `정상 가능성 높음` · `판단불가` · `악성 가능성 높음` · `악성`

* **응답 검증과 근거 연결:** 후처리 검증 코드가 LLM 응답의 필수 항목 누락 여부와 출력 형식을 확인. 이후 모델이 판정 이유로 지목한 항목들을 Context Builder가 생성한 실제 관측 근거 데이터와 매핑하여 사용자 화면에 전달.
* **검증의 범위:** 코드 레벨의 검증은 응답이 정해진 스키마와 참조 무결성을 따르는지 확인하는 과정이며, 설명의 의미적 정확성과 판단 품질 자체는 별도의 성능 평가 지표로 검증.

---

### 7) L4: Agent 기반 심층 분석

빠른 분석 결과와 사용자의 추가 질문을 바탕으로, **격리된 환경에서 페이지의 요구를 실제로 따라갔을 때 어떤 동작이 일어나는지** 동적으로 조사한다. Agent는 현재 화면과 네트워크 관찰 결과를 확인하며 다음 행동을 스스로 결정하고, 새롭게 확보한 정보를 후속 조사에 반영한다.

* **계층적 작업 구조 (Work · Task · Action):**
  * **Work:** 이번 조사에서 답을 얻으려는 상위 업무나 질문 단위
  * **Task:** 해당 업무를 해결하기 위해 개별 도구(Tool) 또는 실행 Agent에 배정하는 단위 작업
  * **Action:** 작업 수행 중 격리 환경에서 실제로 실행하는 개별 행동 (클릭, 입력 등)
* **역할 분리와 도구 구성:**
  * **총괄 Agent:** 전체 업무(Work)를 기획하고 작업(Task)을 배정하며, 기록된 결과를 검토해 추가 조사 여부나 종료를 결정.
  * **Tool 및 실행 Agent:** 수행 절차가 정해진 작업은 단일 Tool이 즉시 처리하고, 화면 반응에 따라 행동을 유동적으로 선택해야 하는 작업은 실행 Agent가 담당. 도구는 브라우저 조작, 페이지 상태 조회, 화면 캡처·네트워크 덤프 확보 등 **전용 도구 17종과 bash를 합쳐 총 18종**으로 구성.
* **격리 실행 환경:** 브라우저와 bash는 일회성 guest 환경에서 안전하게 실행하며, 자격 증명과 외부 저장소 연결 권한은 controller 측에만 두어 격리성을 유지.

## 05. 데이터 파이프라인과 저장 구조

### 생존 URL 확보와 라벨 분리 관리

웹페이지의 콘텐츠와 동작을 분석하려면 수집 시점에 해당 URL에 실제로 접속할 수 있어야 한다. 팀에서 2026년 9월 26일 기준 PhishTank 덤프 약 7.7만 건을 검증했을 때, 실제 접속이 가능한 생존 URL은 **7.2%**에 불과했다.

이에 따라 단순 URL 목록 수집에 그치지 않고, **생존 여부 확인 → 관측 자료 수집 → 라벨 분리 저장**으로 이어지는 전용 파이프라인을 구축했다.

* **수집 경로 이원화:** PhishTank 등 출처 라벨이 존재하는 URL과, CertStream(실시간 인증서 발급 로그) 등에서 확보한 라벨 없는 후보 URL의 처리 경로를 구분.
* **라벨 오염 방지:** **출처 라벨(Ground Truth), LinkGuard 자체 판정, VirusTotal 외부 조회 결과를 별도 필드로 엄격히 분리해 보존**. 라벨이 없는 후보 URL에 대해 LinkGuard가 악성 판정을 내리더라도, 이를 학습이나 평가용 정답 라벨로 그대로 편입시키지 않고 후속 검증 대상으로 관리.

### 원본·분석 결과·진행 기록의 분리 저장

* **S3 저장소 분리:** 수집한 페이지 원본 데이터는 `raw`, 계층별 정적 분석 결과와 근거는 `record`로 구분해 S3에 저장. 모든 자료는 분석 작업(Job) 및 시도(Attempt) 단위로 연결되어 특정 판정이 어떤 시점의 어떤 입력에서 나왔는지 추적 가능.
* **심층 분석 상태 관리:** L4 심층 분석 과정의 조사 기록과 캡처 파일 참조는 S3와 DynamoDB에 나누어 보존하며, 백엔드가 이를 조회해 사용자 화면에 실시간 진행 상황과 최종 근거로 전달.

## 06. 성능 평가 및 검증

### 1) 빠른 분석 성능 평가

* **평가 데이터셋:** 분석 시점에 실제 접속 가능한 정상 URL 500건, 악성 URL 500건 (총 1,000건)
* **평가 조건:** 외부 평판 정보를 판단 입력에서 완전히 배제하고, 순수하게 L0~L3가 수집하고 Context Builder가 재구성한 자체 증거만 제공한 상태에서의 판정 성능을 측정.

발표자료의 기준 설정인 **Sonnet 5.5 medium** 모델 기준 평가 결과는 다음과 같다.

| 평가 지표 | 측정 결과 | 산출 기준 및 비고 |
| :--- | :---: | :--- |
| **전체 정답률** | **89.8%** | 정답 898건 / 전체 1,000건 (판단 유보 74건을 분모에 포함) |
| **판단 유보율** | **7.4%** | 판단불가 판정 74건 / 전체 1,000건 (정답·오답 건수에서는 제외) |
| **오탐률 (FPR)** | **0.2%** | 정상 500건 중 악성으로 잘못 판정한 비율 (1건) |
| **미탐률 (FNR)** | **5.4%** | 악성 500건 중 정상으로 잘못 판정한 비율 (27건) |
| **평균 판정 응답 시간** | **6.74초** | URL 1건당 LLM 판정 API의 평균 응답 시간 (수집 시간 제외) |

동일한 평가셋에서 추론 설정을 높인 **Sonnet 5.5 high** 모델의 경우 전체 정답률은 **90.6%**로 소폭 상승했으나, 평균 판정 API 응답 시간은 **8.34초**로 증가했다. 서비스 응답 지연을 고려해 medium 설정을 기본 기준으로 삼았다.

---

### 2) Context Builder 적용 효과 검증 (Ablation Study)

동일한 1,000건의 평가셋과 동일 모델(Sonnet 5.5 medium) 조건에서, 계층별 원본 결과(`record`)를 그대로 입력했을 때와 **Context Builder**로 맥락을 재구성해 입력했을 때의 차이를 비교했다.

| 비교 지표 | `record` 원본 입력 | Context Builder 적용 | 변화량 |
| :--- | :---: | :---: | :---: |
| **평균 입력 토큰 수** | 56,613 | **21,044** | **-62.8%** |
| **전체 정답률** | 66.8% | **89.8%** | **+23.0%p** |
| **판단 유보율** | 30.6% | **7.4%** | **-23.2%p** |
| **오탐률 (FPR)** | 0.2% | **0.2%** | 유지 |
| **미탐률 (FNR)** | 5.0% | **5.4%** | +0.4%p |

* **주요 개선점:** 중복 제거와 구조화를 통해 평균 입력 토큰을 **62.8% 줄이면서도**, 모델이 파편화된 정보 속에서 판단을 내리지 못해 유보하던 비율을 **30.6%에서 7.4%로 크게 낮추어** 전체 정답률을 23.0%p 끌어올렸다.
* **해석 시 유의점:** 판단 유보가 줄어들고 적극적인 판정이 늘어나면서 미탐률은 5.0%에서 5.4%로 소폭(2건) 증가했다. 따라서 모든 세부 오류 지표가 일방향으로 개선된 것은 아니며, 또한 입력 토큰 감소율이 곧바로 전체 시스템 운영 비용 절감률과 1:1로 대응하지는 않는다는 점을 함께 고려해야 한다.

## 07. 실제 분석 사례

### 사례 1: 인증정보 입력 폼의 외부 제출 구조 포착
* **관측 대상:** 2026년 9월 11일 수집된 호주 통신사(Telstra) 사칭 의심 페이지 (`avd-wix.vercel.app`)
* **분석 내용:** 페이지 화면은 Telstra ID 로그인을 안내하고 있었으나, L3 정적 분석 결과 하나의 `form` 내부에 ID·비밀번호 입력 필드가 존재하고 제출 방식은 `POST`, 제출 목적지(`action`)는 외부 폼 수집 서비스인 `api.web3forms.com/submit`으로 선언되어 있었다.
* **의의 및 한계:** L3는 페이지 제목, 인증정보 입력 필드, 그리고 현재 문서 도메인과 다른 외부 목적지로의 POST 제출 선언 구조를 정확히 연결해 악성 판단의 핵심 근거로 제시했다. (단, 이 기록에서 브랜드 도메인 비교 항목은 미확정 상태였으며, 정적 제출 선언을 확인한 것일 뿐 실제 전송 성공 여부를 동적으로 관측한 결과는 아니다.)

### 사례 2: 외부 평판 탐지 이전에 자체 증거로 포착한 피싱 호스트
* **관측 대상:** 넷플릭스(Netflix) 로그인 화면을 모방한 피싱 호스트 보존 사례
* **분석 내용:** 2026년 10월 21일 최초 확인 시점에는 VirusTotal 기준 **0/93(탐지 없음)** 상태였고, 하루 뒤인 10월 22일 조회에서는 **11/93**으로 악성 탐지가 증가했다. 반면 LinkGuard는 10월 21일 시점에 해당 호스트의 페이지를 즉시 **악성**으로 판정했다.
* **판정 근거 및 해석:** 주소에 포함된 `netflix` 문자열과 실제 등록 도메인 간의 불일치, 로그인 화면 구성, ID·비밀번호 입력 유도 구조를 결합해 내린 판정이다. 두 화면의 세부 URL 경로와 조회 시각에 차이가 있으므로 엄밀한 동일 조건 벤치마크로 해석할 수는 없으나, 외부 평판이 쌓이기 전에 페이지 자체 증거만으로 위협을 식별할 수 있음을 보여주는 사례다.

## 09. 향후 확장 과제

### 1) 로컬 LLM 파인튜닝 및 재평가
수집 파이프라인을 통해 축적한 정답 라벨, 정제된 증거, 판정 이유 데이터를 학습셋으로 구성해 오픈소스 기반 로컬 LLM을 파인튜닝할 계획이다. 학습에 사용되지 않은 시점의 URL 데이터셋을 별도로 분리해 기존 상용 API 모델과 동일한 조건에서 성능을 비교·검증하는 것이 목표다. 이를 통해 외부 상용 API 의존도를 낮추고, 민감한 내부 URL 분석 자료가 외부로 전송되지 않는 온프레미스(기업 내부망) 배포 환경을 지원하고자 한다.

### 2) 온디바이스(기기 내) 경량 URL 검사 앱
수집 파이프라인으로 확보한 특성 데이터를 바탕으로 경량 ML 모델을 학습시켜, 사용자 모바일이나 PC 기기 내부에서 URL 접속 즉시 위험 여부를 1차 판단하고 경고하는 애플리케이션으로 확장할 계획이다. 이를 위해 향후 모델 경량화에 따른 탐지 성능 유지율, 경고 지연 시간(Latency), 기기 메모리 및 연산 자원 소모량에 대한 실증 검증을 진행할 예정이다.
